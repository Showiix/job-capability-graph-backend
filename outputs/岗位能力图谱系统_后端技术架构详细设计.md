## 📋 文档概述

### 编写目的

本文档定义岗位能力图谱系统的后端技术方案，作为后端开发、算法接入、数据库设计、接口联调、部署验证和后续前端设计的共同基线。

系统不是面向公网的大规模企业招聘平台，也不是只读取固定演示数据的静态原型。它的定位是：

> 一套可以在本机或可信内网部署、业务流程真实运行、页面展示完整、能够持续导入并处理招聘数据的内部应用。

系统必须真实完成以下闭环：

1. 批量导入多来源 JD 数据
2. 清洗、标准化、去重和质量检查
3. 调用算法服务和 LLM 提取岗位与技能候选
4. 将候选技能映射到可维护的标准技能库
5. 发现候选技能组合和岗位能力变化
6. 通过人工审核控制正式知识图谱发布
7. 解析应聘者或 HR 上传的简历
8. 计算可解释的人岗匹配和技能差距
9. 基于图谱与 RAG 生成成长路径
10. 保留完整任务、证据、审核和版本历史

### 核心术语

| 术语 | 定义 |
| --- | --- |
| Raw JD | 未经业务清洗的招聘原始记录，保留来源字段和原始正文 |
| Normalized JD | 已完成编码、字段、日期、地区、薪资和正文标准化的 JD |
| Capability | 标准技能实体，是技能身份与名称的唯一真相源 |
| Capability Candidate | 由规则、算法或 LLM 提取，但尚未完成正式确认的技能候选 |
| Job Role | 标准岗位实体，不等同于招聘网站中的原始岗位名称 |
| Graph Change Candidate | 可能新增或修改正式知识图谱的待审核变更 |
| Import Batch | 一次文件导入或未来一次爬虫采集形成的数据批次 |
| Processing Run | 对批次、简历、候选发现或图谱发布执行的一次后台任务 |
| Evidence | 支撑技能、岗位或关系结论的原始文本片段与来源信息 |
| Graph Version | 一次审核发布后形成的正式知识图谱版本 |

## 🎯 目标与边界

### 后端目标

后端必须实现以下能力：

- 管理用户、登录会话与三种角色权限
- 接收 CSV、Excel、JSON、PDF 和 DOCX 文件
- 自动识别标准模板、猎聘格式和智联格式
- 保存原始文件和原始行，不覆盖来源证据
- 执行可恢复、可重试、可取消的后台处理任务
- 支持普通 PDF、DOCX 和扫描 PDF 的文本提取
- 对接算法服务和 LLM API
- 管理标准岗位、标准技能、技能别名和学习资料
- 管理新技能、新岗位和图谱关系的人工审核
- 向 Neo4j 发布审核通过的版本化关系
- 为应聘者和 HR 提供真实的人岗匹配
- 保存匹配明细、硬条件检查和成长路径
- 提供任务、错误、审核、发布和用户操作审计

### 非目标

当前版本明确不实现：

- 公网开放和匿名访问
- 用户自助注册、短信验证、邮箱验证和找回密码
- 多租户企业组织架构
- 企业 SSO、OAuth 和 MFA
- 微服务拆分
- Kubernetes、高可用集群和自动扩缩容
- MinIO 或 S3 对象存储
- LangGraph、通用 Agent Runtime 和 Checkpoint 编排
- WebSocket 和 SSE 事件流
- 招聘网站爬虫的具体实现
- 让 LLM 直接决定最终匹配百分比
- 让算法或 LLM 直接写入正式知识图谱
- 完整在线教育、课程打卡和测验系统
- 算法准确率、模型训练和人工金标准数据集建设

### 设计原则

#### PostgreSQL 保存过程，Neo4j 服务图查询

PostgreSQL 保存业务记录、证据、候选、审核和发布账本。Neo4j 保存审核通过且可查询的岗位能力关系。Redis 不承担任何正式业务事实。

#### 原始数据不可变

原始文件、原始行和来源字段只追加不覆盖。清洗后的结果另表保存，任何标准化结果都能追溯到原始记录。

#### LLM 和算法只产生候选

算法服务和 LLM 可以识别、推断和排序，但不能直接创建标准技能、正式岗位或正式图谱关系。

#### 标准技能库是唯一技能身份源

简历、JD、匹配结果和 Neo4j 图谱都使用同一个 <code>capability_id</code>。原始技能名称只能作为证据和别名候选。

#### 确定性工作自动执行，知识变更人工审核

字段转换、编码修复、精确去重和已知别名映射可以自动完成。新技能、新岗位、能力变化和技能前置关系必须审核。

#### 后台任务状态以 PostgreSQL 为准

Celery 和 Redis 负责投递与执行。任务是否成功、当前阶段、进度、错误和结果都以 PostgreSQL 记录为正式状态。

### 角色与业务范围

| 角色 | 主要能力 | 数据范围 |
| --- | --- | --- |
| applicant | 上传自己的简历、确认画像、匹配岗位、查看差距和成长路径 | 仅本人数据 |
| hr | 创建招聘项目、上传 JD、批量上传候选人、查看排序、审核新岗位候选 | 自己创建或被授权的招聘项目 |
| admin | 导入 JD、任务管理、技能库维护、图谱审核、发布、用户管理 | 全部数据 |

### 关键质量属性

| 属性 | 设计要求 |
| --- | --- |
| 可追溯 | 每个技能、岗位和关系都能定位到来源 JD 与证据片段 |
| 可恢复 | 页面关闭或 API 重启不影响已投递的后台任务 |
| 可重试 | 网络、LLM 和算法服务临时失败可有限重试 |
| 幂等 | 相同任务重复执行不会重复创建正式图谱事实 |
| 可解释 | 匹配分必须拆成技能、经验、学历、项目和硬条件 |
| 可维护 | 新数据源通过 Adapter 接入，不修改后续处理流程 |
| 可演化 | 技能库、Prompt、算法模型和图谱都保存版本 |
| 可审计 | 登录、审核、发布、重试和用户管理操作写入审计日志 |

### 技术栈

| 层级 | 技术 | 选择原因 |
| --- | --- | --- |
| API | FastAPI | Python 生态与算法、OCR、Celery 集成直接，并可生成 OpenAPI[^1] |
| ORM 和迁移 | SQLAlchemy 2 + Alembic | 统一关系模型和数据库迁移 |
| 后台任务 | Celery | 支持独立 Worker、重试和周期任务[^2] |
| Broker | Redis | 当前仅承担 Celery 消息和短期锁[^3] |
| 业务数据库 | PostgreSQL | 保存事务型业务数据、JSON 和审计记录[^4] |
| 向量检索 | pgvector | 在 PostgreSQL 内保存与检索向量，避免独立向量数据库[^5] |
| 图数据库 | Neo4j | 保存岗位、技能和前置关系，支持图遍历查询[^6] |
| PDF 解析 | PyMuPDF | 普通 PDF 文本与页面级提取[^7] |
| DOCX 解析 | python-docx | 提取 Word 段落和表格[^8] |
| OCR | PaddleOCR | 普通解析失败时处理中文扫描文档[^9] |
| 密码哈希 | Argon2id | 保存不可逆密码哈希，不保存明文密码[^10] |
| 部署 | Docker Compose | 单机或可信内网部署，保持组件可重复启动 |

### 数据真相边界

| 数据 | 真相源 | 说明 |
| --- | --- | --- |
| 用户和权限 | PostgreSQL | Redis 中不保存正式会话事实 |
| 原始文件 | Local Volume + PostgreSQL 元数据 | 文件内容在 Volume，哈希和路径在 PostgreSQL |
| 原始 JD | PostgreSQL | 不写入 Neo4j |
| 标准技能与别名 | PostgreSQL | 技能身份唯一真相源 |
| 抽取候选 | PostgreSQL | 算法与 LLM 输出先进入候选区 |
| 审核记录 | PostgreSQL | 每次决定不可被 Neo4j 替代 |
| 正式图谱查询 | Neo4j | 只包含审核通过的岗位能力事实 |
| 图谱发布账本 | PostgreSQL | 支持失败重试、审计和恢复 |
| 匹配结果 | PostgreSQL | 保存图谱版本和权重版本 |
| RAG 文本与向量 | PostgreSQL + pgvector | 检索结果保留来源与版本 |
| 队列状态 | Redis | 可丢弃，不能作为正式状态 |

候选分由以下维度组成，具体权重属于算法配置，不在后端写死：

| 维度 | 后端需要保存的数据 |
| --- | --- |
| 支持度 | 支撑候选组合的 JD 数量 |
| 公司多样性 | 独立公司数量 |
| 来源多样性 | 猎聘、智联等独立来源数量 |
| 组合一致性 | 聚类内部相似度或一致性分数 |
| 岗位差异度 | 与最近似标准岗位的差异分数 |

### Resumes

职责：

- applicant 上传和管理自己的简历
- HR 为候选人上传简历
- 提取 PDF、DOCX 和 OCR 文本

简历解析策略：

### Matching

职责：

- 接收已确认的 Resume Profile
- 查询目标 JD 或 Job Role 的能力要求
- 计算技能、项目、经验和学历维度
- 检查必须条件和优先条件
- 保存可解释明细
- 支持按同一权重版本重新计算

推荐评分结构：

| 维度 | 默认权重 | 说明 |
| --- | ---: | --- |
| 核心技能 | 60% | 岗位必备技能的覆盖与熟练度 |
| 加分技能 | 10% | 岗位优先技能 |
| 项目证据 | 15% | 技能是否在项目或经历中真实使用 |
| 工作经验 | 10% | 必须或优先经验 |
| 学历 | 5% | 必须或优先学历 |

默认权重作为版本化配置保存，不暴露给普通用户随意调整。

匹配输出必须同时保存：

- 技能匹配分
- 综合匹配分
- 已具备技能
- 缺失技能
- 加分技能
- 简历证据
- JD 证据
- 硬条件满足状态
- 每个维度对总分的贡献
- 使用的图谱版本
- 使用的权重版本

职责：

- 自动记录课程进度

## 💾 数据模型

### 数据建模原则

- 主键统一使用 UUID
- 时间统一保存为带时区 UTC 时间
- 对用户展示时再转换时区
- 原始字段和标准字段分表或分列保存
- 状态使用受控枚举或数据库约束
- 所有正式变更保存 <code>created_at</code> 和 <code>updated_at</code>
- 业务记录使用逻辑状态，不随意物理删除
- 大模型和算法原始输出使用 JSONB 保存
- 高频筛选字段建立普通 B-tree 索引
- 向量字段只用于候选召回，不替代关系约束

文件系统使用 UUID 生成的 <code>storage_key</code>，绝不直接使用客户端文件名作为路径。原始文件名只用于展示。

唯一性与索引：

- 索引 <code>sha256</code>
- 索引 <code>owner_user_id</code>
- 不对 <code>sha256</code> 设置全局唯一，以允许同一文件用于不同业务上下文
- 相同用户和同一业务上下文重复上传时由 Service 提示复用

#### raw_job_postings

约束：

- 唯一 <code>(batch_id, row_number)</code>
- <code>raw_payload</code> 保存来源行的完整原始结构
- <code>raw_text</code> 保存用于后续处理的原始正文
- <code>parse_warnings</code> 保存乱码、缺字段、城市冲突和日期不确定等问题
- Raw JD 创建后不允许业务更新

#### normalized_job_postings

标准化规则：

- <code>published_at</code> 无法可靠解析时为空，不伪造日期
- <code>city</code> 优先从真实工作地点解析，不盲信搜索城市
- 薪资统一为月薪区间，原始薪资仍保存在 Raw JD
- <code>duplicate_of_id</code> 指向稳定代表记录
- 质量分仅用于排序和过滤，不删除原始数据

### Neo4j 图模型

第一版节点：

| Label | 关键属性 |
| --- | --- |
| Domain | id、code、name、status |
| Capability | id、canonical_name、status、catalog_version |
| JobRole | id、canonical_name、status、catalog_version |

第一版关系：

| 关系 | 起点 | 终点 | 关键属性 |
| --- | --- | --- | --- |
| BELONGS_TO | Capability 或 JobRole | Domain | valid_from_version、valid_to_version |
| REQUIRES | JobRole | Capability | job_level、importance、required_level、confidence、evidence_count、source_count、valid_from_version、valid_to_version |
| BONUS | JobRole | Capability | job_level、importance、confidence、evidence_count、source_count、valid_from_version、valid_to_version |
| PREREQUISITE_OF | Capability | Capability | strength、confidence、valid_from_version、valid_to_version |
| RELATED_TO | Capability | Capability | relation_kind、confidence、valid_from_version、valid_to_version |

图谱不保存：

- 原始 JD 全文
- 简历全文
- 用户和密码
- Processing Run
- 审核表单
- LLM 原始响应

### 图谱有效版本

关系不是直接覆盖，而是使用：

~~~text
valid_from_version
valid_to_version
~~~

查询版本 <code>V</code> 时，关系有效条件为：

~~~text
valid_from_version <= V
AND
(valid_to_version IS NULL OR V < valid_to_version)
~~~

发布新版本时：

1. 新增关系写入 <code>valid_from_version = new_version</code>
2. 被替换关系写入 <code>valid_to_version = new_version</code>
3. 当前 API 仍使用旧版本号查询，因此旧图不受影响
4. Neo4j 写入验证全部通过后，PostgreSQL 将当前版本切换为新版本
5. 后续 API 使用新版本号查询

这种设计避免发布一半时对用户暴露不完整图谱。

## 🌐 API 与外部集成

### REST 约定

所有业务接口使用：

~~~text
/api/v1
~~~

基础约定：

- 请求和响应默认使用 JSON
- 文件上传使用 <code>multipart/form-data</code>
- 异步任务创建成功返回 <code>202 Accepted</code>
- 同步资源创建成功返回 <code>201 Created</code>
- 登录通过 HttpOnly Cookie 建立会话
- 列表接口使用 <code>limit</code> 和 <code>offset</code>
- 时间返回 ISO 8601 UTC 字符串
- ID 使用 UUID 字符串
- 写操作接受可选 <code>Idempotency-Key</code>
- 每个响应返回或透传 <code>X-Request-ID</code>

### LLM 调用契约

后端使用一个 OpenAI-compatible Client，不建设通用 Model Gateway。

环境配置：

~~~text
LLM_BASE_URL
LLM_API_KEY
LLM_MODEL
LLM_TIMEOUT_SECONDS
LLM_MAX_RETRIES
EMBEDDING_MODEL
~~~

LLM 用途：

- JD 结构化补充抽取
- 新岗位候选定义
- 简历教育、经历和项目抽取
- 成长路径阶段文字和练习项目

LLM 禁止：

- 直接写数据库
- 直接写 Neo4j
- 自由调用外部 Tool
- 自己决定最终匹配百分比
- 输出技能库不存在的正式 Skill ID
- 输出学习资料库不存在的正式链接

每个 Prompt 包含：

1. 明确 System Instruction
2. 当前任务 JSON Schema
3. 检索到的有限证据
4. 标准技能候选
5. 不得扩写或推断无证据事实的约束
6. 原始文本的明确数据边界

LLM 输出必须经历：

1. JSON 语法检查
2. Pydantic Schema 检查
3. Evidence 子串检查
4. Capability 映射检查
5. 来源链接检查
6. 业务状态检查

### 匹配计算

最终匹配分由后端稳定规则计算，不使用 LLM 自报分数。

技能分：

~~~text
skill_score =
100 × Σ(requirement_weight × coverage × level_factor)
      / Σ(requirement_weight)
~~~

其中：

| 变量 | 取值 |
| --- | --- |
| requirement_weight | 岗位技能重要度 |
| coverage | matched=1、partial=0.5、missing=0 |
| level_factor | 满足等级=1、接近等级=0.8、明显不足=0.5 |

<code>partial</code> 只能来自审核通过的 <code>RELATED_TO</code> 图谱关系或人工确认，不能仅因 Embedding 相似就计分。

项目证据分用于区分：

- 只在技能列表中出现
- 在项目描述中真实使用
- 在持续工作经历中真实使用

经验和学历：

- JD 标记为必须时，单独产生 Hard Requirement 状态
- JD 标记为优先时，进入软评分
- 不满足硬条件不删除候选人
- 前端同时展示 Skill Score、Overall Score 和 Hard Requirement Issues

权重配置保存版本，例如 <code>match_weights_v1</code>。历史 Match Result 不随新权重变化。

## ⚙️ 任务可靠性与错误处理

### Processing Run 状态机

~~~mermaid
stateDiagram-v2
    accTitle: Processing Run Lifecycle
    accDescr: Durable processing run lifecycle from creation through execution, review, completion, retry, cancellation, and permanent failure

    [*] --> Pending: Create run
    Pending --> Running: Worker claims
    Pending --> Cancelled: Cancel before start

    Running --> WaitingReview: Candidates require review
    Running --> Completed: Processing succeeds
    Running --> Failed: Retry budget exhausted
    Running --> CancelRequested: User requests cancel

    CancelRequested --> Cancelled: Worker reaches safe point
    WaitingReview --> Running: Approved action continues
    WaitingReview --> Completed: No publication required
    WaitingReview --> Cancelled: Reviewer closes task

    Failed --> Pending: Authorized retry
    Completed --> [*]: Final state
    Cancelled --> [*]: Final state
~~~

### 正式状态与 Celery 状态

Celery Task ID 只用于诊断。API 不直接将 Celery Backend 状态返回给用户。

正式状态流程：

1. API 在 PostgreSQL 创建 Processing Run
2. 事务提交后投递 Celery Task
3. Worker 使用 Run ID 读取任务参数
4. Worker 原子更新状态为 Running
5. Worker 执行阶段并写进度
6. Worker 写 Completed、Waiting Review、Failed 或 Cancelled

如果数据库创建成功但投递失败：

- API 将 Run 标记为 <code>enqueue_failed</code> 或 <code>pending</code>
- 后台 Reconciler 或管理员重试投递
- 不删除 Run

第一版可以使用 Celery Beat 定时扫描长时间 Pending 的 Run 并重新投递，不需要独立调度系统。

### 幂等策略

| 操作 | 幂等键 |
| --- | --- |
| 文件导入 | file_sha256 + user_id + business_context |
| 批次处理 | batch_id + pipeline_version |
| JD 抽取 | normalized_job_id + extraction_version |
| Embedding | content_hash + embedding_model + embedding_version |
| 简历解析 | resume_id + extraction_version |
| 匹配 | resume_profile_id + target_id + graph_version + weight_version |
| 图谱发布 | graph_version_id + publication_operation |
| LLM 调用缓存 | input_hash + prompt_version + model_name |

接口允许用户显式 <code>force_reprocess</code>。强制重跑创建新版本，不覆盖旧结果。

### 重试策略

| 错误 | 自动重试 | 策略 |
| --- | --- | --- |
| LLM 429 或 5xx | 是 | 指数退避，最多 3 次 |
| Algorithm Service 超时或 5xx | 是 | 指数退避，最多 3 次 |
| Neo4j 临时连接失败 | 是 | 有限重试并保持幂等 |
| Redis 临时失败 | 是 | API 返回可重试错误，Run 保留 |
| 无效文件类型 | 否 | 直接拒绝 |
| 缺少必填字段 | 否 | 记录逐行错误 |
| LLM 无效 JSON | 是 | 带修复提示重试 1 次 |
| Evidence 不存在于原文 | 否 | 候选标记 invalid |
| 权限不足 | 否 | 返回 403 |
| 数据库约束冲突 | 视情况 | 幂等冲突转为读取已有结果 |

自动重试只处理瞬时故障。业务错误和输入错误不进行无限重试。

### 合作式取消

Celery 强制终止可能中断数据库或文件操作，因此使用合作式取消：

1. API 将 <code>cancel_requested=true</code>
2. Worker 在每个阶段边界和批量循环检查标志
3. 当前最小事务完成后停止
4. Run 标记 Cancelled
5. 已经完成的原始数据和中间结果保留

图谱发布进入 Neo4j 事务后不响应取消，必须先完成或回滚该事务。

### 并发控制

第一版采用以下最小锁：

- 同一 Import Batch 同一 Pipeline Version 同时只能有一个 Running Run
- 同一 Resume 同一 Extraction Version 同时只能解析一次
- 同一 Graph Version 同时只能有一个 Publication
- 同一用户的相同 Idempotency Key 只能创建一个资源

锁可以使用 PostgreSQL 唯一约束和事务级 Advisory Lock。Redis Lock 只作为性能优化，不能替代数据库约束。

### 进度更新

避免每处理一条记录都更新 PostgreSQL。Worker 按以下任一条件批量更新：

- 每处理固定数量记录
- 每经过固定时间
- 阶段切换
- 出现错误
- 任务结束

前端每 2 至 3 秒轮询一次。完成、失败或取消后停止轮询。

### 图谱发布一致性

发布过程：

1. PostgreSQL 创建 Draft Graph Version
2. 将 Approved Candidate 固定到该版本
3. 创建唯一 Graph Publication 和 Idempotency Key
4. Worker 在 Neo4j 使用稳定 UUID 与 <code>MERGE</code>
5. 新关系写入 <code>valid_from_version</code>
6. 旧关系写入 <code>valid_to_version</code>
7. Worker 按预期数量和关键属性读回验证
8. 验证通过后 PostgreSQL 将 Graph Version 标记 Published
9. Current Graph Version 指针切换到新版本

如果 Neo4j 已提交但 Worker 在更新 PostgreSQL 前崩溃，重试通过相同 Idempotency Key 和稳定关系键识别已有写入，完成验证后继续确认，不重复创建关系。

### 错误分类

| 分类 | 示例 | 用户看到的处理 |
| --- | --- | --- |
| validation | 文件格式、必填字段、非法状态 | 修正输入 |
| authorization | 越权读取、非管理员发布 | 联系管理员 |
| dependency_transient | LLM、算法、Neo4j 临时失败 | 自动重试或手工重试 |
| dependency_permanent | 模型不支持 Schema、服务版本不兼容 | 管理员检查配置 |
| data_quality | 乱码、缺正文、城市冲突 | 批次警告或人工修正 |
| business_conflict | 重复审核、版本已发布 | 刷新后读取最新状态 |
| internal | 未预期异常 | 返回 Request ID，查看日志 |

### 文件安全

上传边界检查：

- 文件扩展名
- MIME 类型
- 文件 Magic Bytes
- 文件大小
- 空文件
- 文件哈希
- DOCX ZIP 解压大小上限
- 文件名路径穿越
- PDF 和 Office 解析超时

存储规则：

- 使用 UUID Storage Key
- 不使用用户文件名作为真实路径
- 文件目录不由 Web Server 直接静态暴露
- 下载必须经过权限检查
- 下载响应使用安全的 Content-Disposition
- 临时解析文件放入独立临时目录并及时清理

### LLM Prompt Injection 防护

JD 和简历都是不可信文本。它们可能包含诱导模型忽略系统指令的内容。

防护规则：

- 原始文本作为明确分隔的数据字段传入
- System Prompt 声明文本中的指令不具备控制权
- 不为 LLM 提供数据库、网络或 Tool 权限
- 强制结构化 JSON Schema
- 只传递完成任务所需的最小证据
- 后端校验 Evidence 是否存在于原文
- 后端校验 Skill ID 是否来自 Catalog
- 无法验证的输出只进入 Candidate 或 Invalid

### 数据最小化

- Algorithm Service 只接收完成任务所需文本
- LLM 请求尽量去除姓名、电话、邮箱和身份证等个人信息
- 日志不保存完整正文
- 普通用户无法读取模型原始调用记录
- 审计记录保存动作，不复制敏感正文
- 删除或停用账号时不自动删除业务审计记录

### 密钥管理

敏感配置只通过环境变量或受控 Secret 文件注入：

~~~text
DATABASE_URL
REDIS_URL
NEO4J_URI
NEO4J_USERNAME
NEO4J_PASSWORD
SESSION_SECRET
LLM_API_KEY
ALGORITHM_SERVICE_TOKEN
~~~

禁止：

- 提交真实 <code>.env</code>
- 在代码中写密钥
- 在 API 响应中回显密钥
- 在异常堆栈中打印连接字符串
- 将用户提供的 API Key 保存进普通业务表

## 📦 部署、验证与实施顺序

### Docker Compose 服务

| 服务 | 进程 | 持久化 |
| --- | --- | --- |
| web | 前端 Web Server | 无正式业务数据 |
| api | FastAPI/Uvicorn | 无本地状态 |

| scheduler | Celery Beat | Schedule 文件可放 Volume 或使用数据库调度 |

### 启动顺序

1. PostgreSQL、Redis 和 Neo4j 启动

3. 创建初始管理员和三种演示账号

5. FastAPI、Worker 和 Scheduler 启动
6. Web 启动

### 健康检查

| 接口 | 检查内容 | 失败行为 |
| --- | --- | --- |
| GET /health/live | 进程事件循环可响应 | 容器重启 |
| GET /health/ready | PostgreSQL、Redis、Neo4j 必需依赖 | 从服务流量摘除 |
| GET /health/dependencies | 依赖明细，仅 admin | 诊断 |
| Algorithm /health | 模型服务存活 | 算法任务暂停或失败 |
| Algorithm /model-info | 模型已加载及版本 | 阻止不兼容任务 |

LLM 是外部服务，不应因为一次短暂不可用导致 API Readiness 失败；对应业务任务按重试策略处理。

### 数据库迁移

- 使用 Alembic 管理 PostgreSQL Schema
- Migration 进入代码评审
- 禁止应用启动时自动生成 Migration
- 破坏性 Migration 先备份
- 大表变更分阶段执行
- Neo4j Constraints 与 Index 使用版本化初始化脚本
- Graph Schema 变化与 Graph Version 分开管理

### 备份与恢复

必须备份：

- PostgreSQL
- Neo4j
- 文件 Volume
- Algorithm Model Weight
- 部署配置模板

Redis 不需要作为业务恢复来源。

恢复顺序：

1. 恢复 PostgreSQL
2. 恢复文件 Volume
3. 恢复 Neo4j
4. 校验当前 Graph Version
5. 启动 Algorithm Service
6. 启动 API 和 Worker
7. 扫描 Pending、Running 和 Publishing 状态
8. 将失去 Worker 的 Running Run 标记为可恢复并重新投递

如果 Neo4j 数据损坏，可以依据 PostgreSQL 中的 Published Graph Version、Change Candidate、Review Decision 和 Publication Ledger 重新构建正式图谱。

### 主要风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 来源数据乱码或缺字段 | 抽取质量下降 | Raw 数据保留、Adapter 警告、质量分 |
| 相似 JD 抄袭和复制 | 候选支持度虚高 | 精确去重、相似簇、代表记录 |
| LLM 幻觉 | 错误技能和岗位定义 | Evidence 校验、Catalog 映射、人工审核 |
| 算法与 LLM 冲突 | 候选不稳定 | 保存双方输出、统一合并规则、待审核 |
| 技能别名歧义 | 错误归一化 | 歧义检测，不自动映射 |
| 图谱发布部分失败 | 正式图不一致 | 版本隔离、幂等发布、读回验证 |
| Worker 重启 | 任务中断 | PostgreSQL 正式状态、重投递和幂等 |
| 外部 API 不可用 | 抽取任务失败 | 有限重试、持久化已有结果 |
| 简历隐私泄漏 | 敏感信息暴露 | 权限、所有权、日志脱敏、受控下载 |
| 组件过多 | 本地运维成本 | 模块化单体、Compose、无微服务拆分 |

### 最终架构结论

系统采用：

~~~text
Web
→ FastAPI 模块化单体
→ PostgreSQL + pgvector
→ Neo4j
→ Celery + Redis
→ 独立 Algorithm Service
→ 云端 LLM API
→ 本地文件 Volume
~~~

这一方案保留了真实批处理、人工审核、版本图谱、简历匹配和成长路径所需的基础能力，同时明确删除了当前不需要的企业级复杂度。
